# MOC Data Methodology

## What is MOC Data?

MOC (Model / Capability / Configuration) data is the static or semi-static data in 9Router that describes external providers, their models, capabilities, pricing, and transport configuration. This data is **sourced from upstream providers** (or manually curated based on provider documentation) and can become **stale** when providers change their APIs, add/remove models, alter pricing, or deprecate features.

## Why This System Exists

1. **Detect upstream drift before it breaks builds.** When `providerModels.js` changes (a model is renamed or removed), we can immediately identify which executors, translators, and tests reference that model — and fix them before shipping.

2. **Know when to reinvestigate.** Every MOC entry records `lastInvestigated` timestamp. When revisiting the project after months, we can see which data is stale and needs re-verification against upstream documentation.

3. **Fail-fast on stale data.** When changing MOC data, the INDEX.md's `consumers` field tells us exactly which code files need updating — no silent breakage.

4. **Track provenance.** MOC data may be:
   - *Static* — manually curated from provider docs
   - *Synced* — auto-generated from a source (e.g., registry/index.js is auto-generated from registry/{id}.js files)
   - *Fixture* — test fixtures mirroring real API shapes

## The Index

The index lives at `docs/moc/INDEX.md`. Every MOC data file has an entry containing:

| Field | Description |
|---|---|
| `File` | Relative path from repo root |
| `Lines` | Total LOC (rough size indicator) |
| `Nature` | `static`, `synced`, or `fixture` |
| `Version` | Git hash + timestamp of last commit touching this file |
| `Last Investigated` | ISO date when we last verified this data against upstream |
| `Consumers` | Files that import/depend on this data |
| `Notes` | Any caveats about staleness risk or update procedure |

## How to Update

### When you add or modify MOC data:

1. Make your change to the data file.
2. Update its entry in `docs/moc/INDEX.md`:
   - Bump version to the current commit hash.
   - Set `lastInvestigated` to today's date (since you just touched it).
   - Verify consumers list is still accurate — add any new importers found via `grep`.
3. Commit both the data change and the index update together.

### When you reinvestigate stale data:

1. Check `lastInvestigated` in the index. If > 90 days old, it's likely stale.
2. Re-check upstream documentation or API for changes.
3. Update the data file if needed.
4. Update the index entry: new `lastInvestigated` + new version if changed.

### When you add a new MOC data file:

1. Add it to `docs/moc/INDEX.md` with all fields populated.
2. Run `grep -rl '"open-sse/config/' open-sse/ src/ cli/ --include='*.js'` (or similar) to find consumers.
3. Commit both files together.

## Enforcement

- Every commit touching a file listed in INDEX.md **must also update** the index entry for that file (version + lastInvestigated).
- The index is version-controlled alongside the data — it is not generated by a CI step, but manually maintained.
- If you see an index entry with `lastInvestigated` older than 180 days, flag it for reinvestigation.
